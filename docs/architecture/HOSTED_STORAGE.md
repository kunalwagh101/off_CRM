# Hosted storage — data that survives a deploy on the free plan

**Status: phases 0 and 1 DONE (2026-10-02); phase 2 built, in review
(2026-10-03).** `S-06.03.01` is the inventory below; with `S-06.03.02`, provider
keys, AI settings and trust, the usage counters, logins and the egress log live
in the database `OFFSETX_DATABASE_URL` names; with `S-06.03.03`, so does the
CRM — campaigns, contacts, drafts, sends, replies and delivery jobs — for the
web app and every command-line tool. Answers `Q-26` with the owner's choice of
2026-09-25: keep Render free, and keep the data in a hosted PostgreSQL. Stories:
`S-06.03.01` to `S-06.03.06` (feature `F-06.03`). Decision: `DD-66`.

## Why

On Render's free plan the service's disk is `/tmp`, wiped on every deploy and
restart. Everything under `OFFSETX_DATA_DIR` goes with it: the CRM, the
encrypted provider keys **and the master key that decrypts them**
(`ai/workspace.py`, `.ai_master.key`), workspace logins, audit records. A key
the owner types into Connectors today is gone at the next push.

The owner's rule, which this design keeps: **a user adds provider keys in the
app, never in the server's environment.** Keys typed in the app must therefore
live somewhere a deploy does not touch.

## The one thing the operator sets once

A server that keeps its data elsewhere has to be told where. Two deployment
settings, set once when the install is created, like a house key:

| Setting | What | Who sets it |
|---|---|---|
| `OFFSETX_DATABASE_URL` | the hosted PostgreSQL address | the install owner, once |
| `OFFSETX_SECRETS_KEY` | the master key that encrypts every stored provider key | the install owner, once; generated by a command, never typed |

Neither is a provider key, and no user ever sees them. Every provider key is
still entered in the app, encrypted with the master key, and stored in the
database. A separate secret from `OFFSETX_SESSION_SECRET` on purpose: rotating
the login-signing key must not make every stored provider key unreadable.

## Which host

**Any PostgreSQL 13 or newer — the code must not care.** The owner, 2026-10-02:
start on Render's or Neon's PostgreSQL, and build so the same install moves to a
PostgreSQL on AWS or Azure once there is funding or real users. Nothing in the
code names a host; moving is a `pg_dump` and a `pg_restore`.

| | Render free | Neon free | Supabase free | Paid: Render, AWS RDS, Azure |
|---|---|---|---|---|
| Lasts | **deleted with all its data 30 days after creation, plus 14 days' grace to upgrade** | no expiry | **paused after a week idle; unpaused by hand** | while paid |
| Storage | 1 GB | 1 GB per project, 20 GB per account | 500 MB | chosen |
| Backups | **none, of any kind** | 6 hours of history | none | daily backups and point-in-time restore |
| Idle | — | compute sleeps after 5 minutes, wakes on the next query | — | — |
| Limit | one free database per Render workspace | — | — | — |

Checked on 2026-10-02 (`render.com/docs/free`, `neon.com/docs/introduction/plans`);
Neon's storage was 0.5 GB when first checked on 2026-09-25, and is now 1 GB, with
100 compute-hours a month per project. The same Render page: a free web service
also loses its disk when it spins down after 15 minutes idle, not only on a
deploy — so on the free plan the data folder lives minutes, not days.

**Recommendation.** Neon free to start: it costs nothing and does not expire.
If the database should sit next to the app on Render, a paid Render database
from day one, reached by its *internal* URL in the same region (Singapore).
Render's free database is a trial only — it is deleted with everything in it.
Supabase's pause is disqualifying for an app whose owner may not log in for a
week. On every free option, backups are this install's own job (`S-06.03.04`),
and 1 GB means files do not go in the database.

### What keeps it portable

Built in `S-06.03.02`, each for a host the owner named:

- **One URL.** `OFFSETX_DATABASE_URL` is passed to the driver untouched, so the
  host's own options ride in it: `sslmode=require` for Neon, Render's external
  URL, AWS and Azure; `sslrootcert=` for AWS's certificate bundle.
- **Only a PostgreSQL URL.** Anything else in `OFFSETX_DATABASE_URL` — a
  key/value connection string, a URL in quotes — is refused at start without
  being repeated (`D-206`); an absolute SQLite path is the one exception, for a
  machine with its own disk and for the tests.
- **A dropped connection is reopened.** Neon's compute sleeps; AWS and Azure
  close idle connections behind their load balancers. A connection idle for a
  while is checked before use and reopened if the server dropped it, and the
  network is asked to notice a silent drop in about 15 seconds (`D-208`). A
  statement that fails mid-flight is never sent again by itself — whether it
  ran is unknown — so a drop during active use fails that one request with a
  sentence, and the next one reconnects.
- **Pooled URLs work.** No server-side prepared statements, which a pooler in
  transaction mode — PgBouncer, Neon's pooled URL, RDS Proxy — would break.
- **A schema version per store** (`offcrm_schema`), so a database moved to a
  new host, or opened by a newer release, is upgraded from where it is.
- **The key that opens the provider keys stays out of the database.**
  `OFFSETX_SECRETS_KEY` comes from the environment, which is where AWS Secrets
  Manager and Azure Key Vault deliver a secret. Fernet tokens leave rotation
  open (`MultiFernet`) without rewriting the stored rows; rotation itself is
  not built.

## Switching it on

The install owner does this once per service — a database for each: `develop`
runs unreviewed code and must never reach `main`'s keys.

1. Make a PostgreSQL database: Neon (free, no expiry), a paid Render database,
   or AWS or Azure later. Copy its connection URL. From Render, inside the same
   region, use the *internal* URL; from anywhere else the URL must carry
   `sslmode=require`.
2. Run `offsetx-db new-secrets-key` on any machine with off_CRM installed. Keep
   what it prints in a password manager: it is stored nowhere else, and without
   it nobody can read the provider keys in the database.
3. Set `OFFSETX_DATABASE_URL` and `OFFSETX_SECRETS_KEY` where the service's
   environment is set (on Render: the service's Environment page), and deploy.
4. `/health/ready` answers `ready`; type the provider keys in Connectors again,
   once — the ones typed before were on the wiped disk. The CRM starts empty in
   the database for the same reason; from now on it outlives every deploy.

If the data folder already holds keys, settings or logins — a server with its
own disk, not Render's free plan — the app refuses to start and names the
files (`D-210`). `offsetx-db import-local --yes` copies them into the database,
the keys decrypted with the folder's own key and stored again under
`OFFSETX_SECRETS_KEY`; `offsetx-db import-local --skip` keeps the database as it
is. Either way the files are not touched, so unsetting the two settings goes
back to them. The egress log has its own command, `offsetx-db copy-log`.

The CRM is asked the same question, separately (`S-06.03.03`). If its file
(`OFFSETX_OUTREACH_DB`) holds campaigns, contacts or anything else the owner
put there, the start stops and names `offsetx-db import-crm --yes`, which
copies the file into the database's CRM, and `offsetx-db import-crm --skip`,
which starts on the database's CRM as it is. The built-in templates and notes
every start writes are not counted (`DD-74`): a file holding only those starts
straight away. The file is never changed, so unsetting the URL goes back to it.

`offsetx-db copy-crm --from X --to Y` copies a whole CRM either way — a file
into a database, or a database back into a file, which is the way out. Only
into an empty CRM; one transaction, so a failure leaves it empty; the source
read at one moment and never written; every table's count printed and
compared, the URL's password never shown. 9,442 rows took 1.6 s to a local
PostgreSQL 16 and 0.9 s back; over the network to a hosted one it is slower,
by a round trip per 200 rows, and that has not been measured.

The web app, `offsetx-email-worker`, `offsetx-outreach` and `offsetx-notebook`
all open the CRM by one rule: a `--db` or `--database` given on the command
line, then `OFFSETX_DATABASE_URL`, then `OFFSETX_OUTREACH_DB`. A worker on
another machine therefore needs the same two settings as the app, or it works
an empty file and sends nothing.

What the app does with them: half the pair, or a key that is not a key, stops
the start with a sentence saying what to set. A key that cannot open what the
database holds stops the start too — checked before anything is served, even
before any provider key is stored. A lost key is not recoverable by anyone:
`offsetx-db forget-provider-keys --yes` clears the stored keys so the app
starts with a new one, and each workspace pastes its keys again; settings,
limits, trust and logins stay.

### Limits, plainly

- **Files are still on the wiped disk**: uploaded media, rendered video, the
  local mail outbox and exports (see below), and the stores the inventory marks
  "not decided" (`S-06.03.06`).
- **Expert search is plainer on PostgreSQL.** SQLite ranks the expert library
  with its full-text index (BM25); PostgreSQL has no such index here, so search
  keeps notes holding any of the question's first six words (of three letters
  or more) and returns the newest first, not the most relevant.
  Drafts that draw on a large expert library may pick less relevant notes
  there. Moving it to PostgreSQL's own full-text search is not built.
- **Accented letters fold on PostgreSQL only.** Search ignores A–Z case on
  both backends; "évora" finds "Évora" on PostgreSQL but not on SQLite, whose
  `lower` folds ASCII alone (`DD-75`).
- **Several installs on one database.** Whether a local CRM file was copied in
  or skipped is recorded once per database, as phase 1's keys and logins are:
  a second install's file is then neither asked about nor named
  (`S-06.03.07`).
- **Local backup is refused while anything is hosted**, as it already was for
  the egress log: it cannot capture the database. Backups of the hosted
  database are `S-06.03.04`; until then, the host's own history is all there
  is — 6 hours on Neon free, none on Render free.
- **One connection per store.** Fine for one instance and a handful of people.
  When session checks wait on each other — p95 above 200 ms, or a second web
  instance — the stores move to `psycopg_pool`; the seam allows it.
- **The usage counters are read once per process** and written after each
  call. Two processes counting at once — the app and the eval tool — keep the
  last one's numbers, as two processes sharing the file always did.

## What does not change

- The seam: stores already open their database through
  `db/connection.py::open_database`, and the egress log already runs on
  PostgreSQL (`docs/architecture/POSTGRES.md`). Phases 1 and 2 put more stores
  behind the same seam. The CRM store knows which backend it has in four
  places only — opening, transactions, its first schema, and search's
  index — and runs the same SQL everywhere else.
- The AI rules in `AGENTS.md`: the key vault moving to a database changes where
  ciphertext rests, not who may read it. No model gets a query path to it
  (rule 6).
- Local installs: with no `OFFSETX_DATABASE_URL`, everything stays in SQLite
  under `OFFSETX_DATA_DIR`, exactly as today.

## Risks

- **Compute hours.** 100 CU-hours a month is about 400 hours at the smallest
  size. The scheduled jobs keep the database awake while the service runs; on
  Render free the service itself sleeps when idle, which helps. The design
  asked for a week of phase 1's real usage before the CRM moved; the owner
  chose not to wait (2026-10-03), so the CRM's load on compute hours is
  unmeasured until a real install runs on it. `offsetx-email-worker --watch`
  opens the CRM every `--poll-seconds` (2 by default): about 11 statements a
  time, which alone keeps a Neon compute awake around the clock. On a hosted
  install run it with `--poll-seconds 60` or more, or not at all where the web
  app's own timer sends. A database that is away for a moment no longer ends
  it: it says so and tries again, waiting longer each time up to a minute.
- **Latency.** Every query crosses the network; a cold database takes a moment
  to wake. Screens must show loading, never a blank.
- **Migration on live data.** The copy and its inverse have run on a CRM the
  app's own engine wrote — 9,442 rows, 10.1 MB, every value compared after the
  round trip — not yet on the owner's real CRM, which was not available. Run
  `copy-crm` on a copy of it first.
- **Two stores for one install during phase 1** (keys in the database, CRM
  still local and wiped): acceptable for the free demo, and the reason phase 4
  exists — production refuses the half state.

## Reversal cost

Expensive, not irreversible: PostgreSQL is PostgreSQL, so changing host is a
dump and a restore, and the SQLite path stays for local installs. The cost is
the work in phases 1–2 and the network dependency they add.

### 2026-11-02 — S-06.03.06 timer-settings delivery slice

When `OFFSETX_DATABASE_URL` and `OFFSETX_SECRETS_KEY` configure a hosted
installation, the email and content automation services now read/write named
`timer.email` and `timer.content` documents in `offcrm_documents`. These
settings persist across deletion of the local data folder; writes are wrapped
in the existing cross-process database transaction lock. The local JSON
behaviour is unchanged for installations without a hosted database.

A pre-existing local timer settings file prevents the hosted install from
starting rather than being silently ignored or overwritten. The operator
must first preserve and explicitly migrate the settings. There is no automatic
migration, no new scheduling side effect, no new independent worker and no
change to the free-plan filesystem for assets or outboxes. A database outage
fails the write and never falls back to disposable files. Existing scheduled
tasks still require an independently supervised worker and duplicate-effect
checks before multi-instance use. All other `S-06.03.06` stores remain
unresolved; this slice does not complete F-06.03 or lift production blockers.

## Legacy scheduler migration (operator-only, 2026-11-02)

A hosted installation with a remaining `automation.json` or
`content_automation.json` refuses to boot rather than ignoring old consent.
Stop the web app and every email/content worker. Set `OFFSETX_DATABASE_URL`
and `OFFSETX_SECRETS_KEY` for this *same* installation, and choose an
access-controlled **persistent** archive directory outside the data root.
Then deliberately choose **one**:

```bash
offsetx-db import-timers --data-dir /old/offsetx-data --archive-dir /durable/private/timers --yes
offsetx-db import-timers --data-dir /old/offsetx-data --archive-dir /durable/private/timers --skip
```

- `--yes`: archives both original JSON files unchanged, imports the settings
  into hosted documents, but disables automation, Gmail live-send consent and
  every content posting pair. Re-enable only through the approved app controls.
- `--skip`: archives old files unchanged and keeps the hosted values; nothing
  new is scheduled by this command.
- Both modes refuse symbolic-link sources, archive collisions, unprivate archive
  locations, a concurrent workspace operation, a pending restore and ambiguous
  hosted records. All local source filenames are removed **only** after archive
  fsync and successful hosted transaction. On an interruption, the protected
  originals and database state permit a checked retry; no silent overwrite.
- The archive directory is chosen by the operator. A folder under the free
  Render service or an ephemeral disk **is not a durable backup**, even if
  permissions are 0700. The tool has not been run on a customer installation.
- Current supported configuration migration does not migrate media files,
  mail/post outboxes, CRM databases or OAuth tokens. It is not an independent
  production worker. See `S-06.03.04`, `S-06.03.06`, `S-06.02.40`.

Rollback: with the app/worker stopped, verify the archived JSON copies on a
persistent disk, recover the prior local configuration if necessary, and use
the previous application release. Do not delete hosted documents automatically
or start two timer instances against the same queue.

### 2026-11-02 — S-06.03.06 AI context hosted-storage slice

When an explicit `OFFSETX_DATABASE_URL` is configured, AI task progress,
owner decisions, template-performance counters, winners and workspace-scoped
template records now use versioned tables in the hosted database. The local
install continues to use its existing SQLite `ai_context.db` without changes.
Database failures do not fall back to a temporary local file.

A pre-existing local `ai_context.db` file blocks a hosted start. This avoids
silently discarding client task decisions and conversion statistics. **This
slice does not yet provide an operator-approved importer for the existing
file**; preserve that file on durable storage until the importer is tested.
The other non-hosted stores in S-06.03.06, including sent mail recall, agent
routines, meetings, media and outboxes, remain open. This is not production
backup/restore acceptance or a completed S-06.03.06 story.
