# Work order — S-06.02.24 every process that writes the workspace holds its lease

## ID
S-06.02.24 — Every process that writes the workspace holds its lease.
Board: READY. Fixes `D-134` and `D-138`. Size S.

## GOAL
Every command-line tool that opens a store under `OFFSETX_DATA_DIR` takes the
same shared workspace lease the web requests and the email worker already take,
refuses to run while a restore is pending, and opens the same files the web app
does. A write made during a restore must never land in the generation that the
restore is swapping out.

## BLAST RADIUS / CONSUMERS
Entry points in `pyproject.toml` `[project.scripts]` that open workspace stores:

| Entry point | Module | Opens under the data directory |
|---|---|---|
| `offsetx-outreach` | `outreach_cli.py` | the CRM database — every command except `campaign-kinds`; `gmail-authorize` writes the Gmail token |
| `offsetx-notebook` | `notebook_cli.py` | the CRM database, and the AI context database when `--context` is given |
| `offsetx-evals` | `ai/eval_cli.py` | `ai_evals.db`, `ai_egress.db`, quota files |
| `offsetx-tools` | `ai/tool_cli.py` | `ai_tools.db`, `sandbox/<tool>` |
| `offsetx-db` | `db_cli.py` | `ai_egress.db` — its default is still `local_data/ai_egress.db` |

Already correct, do not change: `offsetx-web` (requests take the lease in
`RecoveryMiddleware`), `offsetx-email-worker` (`D-129`). Checked and not
workspace writers: `offsetx-apollo`, `offsetx-codegraph`, `offsetx-artifacts` —
re-check each with `grep -n "data_dir\|from_env\|local_data" <module>` before
you start, and add any that turns out to write.

A CLI holding the shared lease makes a restore answer 409 "Workspace is busy".
That is the intended behaviour, and the reason for this story.

## ROOT CAUSE
The WP1 port (`S-06.02.21`) applied `WorkspaceLock` to web requests, the
in-process timers and the email worker. The other entry points were not part of
the port. Separately, `D-127` moved the CLIs' CRM default onto
`offsetx_apollo_builder/data_paths.py`, but two defaults were left behind:
`outreach_cli.py`'s Gmail token (`local_data/gmail_token.json`) and
`db_cli.py`'s egress log (`local_data/ai_egress.db`).

## DESIGN
One helper in `offsetx_apollo_builder/outreach/workspace_lock.py`, beside
`WorkspaceLock` (no import cycle: `outreach/backup.py` imports nothing from it):

```python
@contextmanager
def cli_workspace_lease(data_dir: Path) -> Iterator[None]:
    """The shared lease for a command-line tool; refused while a restore is pending."""
    try:
        with WorkspaceLock(data_dir):
            # Checked under the lease, as the email worker does (D-129).
            if restore_pending(data_dir):          # from .backup
                raise WorkspaceBusy("restore pending")
            yield
    except WorkspaceBusy as exc:
        raise SystemExit(
            "A backup restore is in progress or waiting to be rolled back. Start "
            "the web app if it is stopped, and retry once its readiness check passes."
        ) from exc
```

Each writing CLI wraps the command that opens stores in it, around the whole
command, not only the write: an open connection on the old generation is the
hazard. The data directory is `data_paths.data_dir(Path.cwd())`, or the
command's own `--data-dir` where it has one (`eval_cli`, `tool_cli`).

Default paths (`D-138`):
- `outreach_cli.py` `gmail-authorize`: token default becomes
  `os.getenv("OFFSETX_GMAIL_TOKEN")` or `data_paths.data_dir(Path.cwd()) / "gmail_token.json"`
  — the web app's rule in `api/config.py`.
- `db_cli.py`: the egress default becomes
  `data_paths.data_dir(Path.cwd()) / "ai_egress.db"`, keeping any explicit
  argument as is. Update its usage text (line 7) to match.

A command that opens nothing (`campaign-kinds`, `--help`) takes no lease.

## TEST (write it first, watch it fail)
In `tests/test_cli_workspace_lease.py`, parametrised over the five entry
points, each with one harmless command that opens a store (for example
`["create-campaign", "Lease check"]` for the outreach CLI; seed what a command
needs with the stores' own APIs, never by hand-written SQL):

1. **Restore in progress.** Hold `WorkspaceLock(data_dir, exclusive=True)` and
   run the CLI's `main([...])` with `OFFSETX_DATA_DIR` pointing at `data_dir`.
   It raises `SystemExit` whose text contains "restore", and the store file it
   would have opened was neither created nor changed (compare size and mtime).
2. **Restore awaiting rollback.** Build a pending restore with
   `tests/test_workspace_lock.py::_pending_restore` and run the same command:
   refused the same way.
3. **Released afterwards.** A normal run succeeds, and straight after it
   `WorkspaceLock(data_dir, exclusive=True)` can be taken.
4. **`D-138`.** In `tests/test_default_data_paths.py`: with only
   `OFFSETX_DATA_DIR` set, the Gmail token path `gmail-authorize` would write
   and the `offsetx-db` default egress path both sit under that directory.
