# Work order — S-06.03.04 Hosted PostgreSQL backup and recovery

## Goal
An owner-controlled nightly encrypted export of the *actual hosted PostgreSQL* lives outside the database/service. The install owner can download the backup and restore it into a disposable empty PostgreSQL database with reconciled table counts. Do not confuse a local SQLite ZIP with a hosted database backup.

## Read and preserve
`AGENTS.md`, `docs/architecture/HOSTED_STORAGE.md`, `offsetx_apollo_builder/db_cli.py`, `offsetx_apollo_builder/api/production_runtime.py`, `offsetx_apollo_builder/outreach/backup.py`, `offsetx_apollo_builder/db/connection.py`, `tests/test_hosted_storage.py`, `tests/test_crm_hosted.py`. The existing local encrypted backup path must remain intact, and hosted local-backup refusals remain until a real PostgreSQL export/restore exists.

## Readiness and external decision
`S-06.03.03` is DONE. **Q-29 is open**: owner-approved separate durable backup destination, credentials/permission scope, rotation and retention, and unlock-key custody. Do not choose a backup service silently or write backups to Render's ephemeral filesystem or the same database. This work order is preparation only until Q-29 is answered and the real PostgreSQL runner/restore target is available.

## Acceptance — red before green
1. With a real hosted database containing CRM, logins, encrypted provider settings and audit events, export a consistent database snapshot, envelope-encrypt it with a separately managed key, and store it at the authorised offsite destination. Re-run after the process/container is destroyed; the export remains accessible outside the app and primary database.
2. Delete or isolate the test database and restore the export into a new empty PostgreSQL database. Reconcile per-table row counts and spot-check integrity, ownership, key validity and next-sequence values. Never restore over active production state by accident; explicit install-owner approval and a unique destination are required.
3. Simulate encryption-key mismatch, failed upload, partial export, lost remote access, checksum mismatch and failed restore. The job emits a secret-safe failure reference; it does not report success or overwrite the last valid backup. Bound retries, storage cost, data size and schedule concurrency. Owner download returns only ciphertext.

## Rollback, gates
No automatic deletion of a good historical backup. Any rollback must keep the previous verified export readable and turn off scheduling safely. Tests: focused export/restore PostgreSQL integration, existing local-backup regression, full `uv run pytest -q`, `uv run python scripts/verify_board.py` plus actual remote destination + restore demonstration. No DONE claim without real target, runner, owner download and recovery evidence.

## 2026-11-21 — D-475 object read-back acceptance

The prior S3 export checked `head_object` metadata and encrypted file size, but those fields alone do not establish the actual uploaded bytes match. A same-sized corrupted ciphertext with unchanged user-set SHA256 metadata would be reported as exported. Add a streamed `get_object` read-back of the ciphertext, compare SHA256 and byte length, and withhold success on any mismatch or unavailable remote GET. Never download plaintext, use bounded chunk memory, and hide untrusted adapter error contents. The cost is **one additional full encrypted-object download per backup**, plus object-store request/egress charges. This does not replace a scheduled separate recovery drill or an approved independent bucket. Tests include same-length corruption and read-back failure, followed by full real PG backup and restore gates.


## 2026-11-21 — D-476 recovery-target non-table objects

Review found that a database with no application tables could still have a user-defined text-search dictionary or publication. Both are owned state; neither should be silently included in the destination of a restore. Test-first real PostgreSQL cases were added to `tests/test_hosted_backup.py` on efe4700, followed by a catalogue preflight update for `pg_ts_dict` and `pg_publication` in `db/hosted_backup.py` on 2488513. Do not move S-06.03.04 to DONE without the actual test results, a separate approved offsite destination, key custody and disaster-recovery drill.

## 2026-11-21 — D-478 large-object destination preflight

An otherwise table-free PostgreSQL database may still contain large objects in pg_largeobject_metadata. D-478 adds a real CREATEDB integration fixture that creates a large object, expects restore to refuse, removes the object and then allows ordinary restore. RED test source dc22f87; guard source d11eba5. The test and GitHub/Render gates need exact-source output before certification. This protects existing data; it is not an offsite restore drill. Keep the feature unshipped without real independent storage, key ownership and documented rollback.

## 2026-11-21 — D-479 secret-safe S3 adapter failure boundary

A failed S3 upload, metadata HEAD or owner ciphertext download could previously raise a raw adapter exception (including arbitrary secret-looking diagnostic text). New tests inject hostile errors at all three operations (715c694). Application catches adapter errors and raises actionable HostedBackupError with suppressed causes (dc3593a); a partial local download is removed before returning failure. Keep external owner-approved bucket, retention, key custody and recovery drill blocked until physically verified. Real source-specific CI and Render review image require successful results before marking security acceptance complete.

## 2026-11-21 — D-481 private custom S3 hostname refusal

The S3 backup URL validator's numeric-IP check did not reject `localhost`, single-label endpoints or known internal suffixes. Parametrised test source ea4ffc1 exercises seven hostnames with a monkeypatched SDK client; production preflight 3798e3f now rejects them before client construction. An attacker-controlled public DNS name may still resolve/rebind to a private address; no claim of complete network-level SSRF protection. Production must use a vetted endpoint and network boundary. Offsite recovery and key custody remain unmet.

## 2026-11-21 — D-484 unsafe owner download parent links

The owner-controlled ciphertext download checked the filename for existing files/symlinks but allowed a symlinked parent directory. Test-first synthetic parent redirect in tests/test_hosted_backup.py (f6300c6) expects HostedBackupError before reading the object; source guard fbb9ebf refuses existing linked ancestors. The separate runner still needs filesystem ownership, non-user-writable directories and real recovery acceptance. This is not a complete defence against local directory swap races.


## 2026-11-21 — D-493 secure backup-key generation

The operator command `offsetx-db new-backup-key` must never print the
independent decryption key to noninteractive stdout (CI, service logs or shell
pipes). Run it in a private interactive terminal, or run
`offsetx-db new-backup-key --output /private/path/backup.key` to create a
new exclusive mode-0600 file. Existing destinations and final symlinks are
refused; the resulting key is not printed in file-output mode. Store the key
in an independent password manager/KMS and remove the temporary file only
after the protected copy is verified. Losing it permanently loses access to
the encrypted backup.

TDD RED tests `2b0b196` and code `ea720ab` cover both hosted provider and
backup key generation, including non-TTY refusal and output permissions.
This does not prove a remote bucket, scheduled exports, retention, real
recovery, or any independent penetration test. Keep S-06.03.04 open.

## 2026-11-21 — D-495 linked parent directory rejection

The private key writer already used `O_EXCL|O_NOFOLLOW` to reject overwritten files and final symlinks. An operator-selected key path could nevertheless traverse a symlinked parent and write into another location. Added two test-first path-redirection cases (`a9e6cea`) and a preflight rejection (`5a5baf2`). This is a practical guard, **not an atomic protection against a malicious local user racing directory changes**. Genuine backup key files must be generated under trusted, access-controlled directories. Remote bucket/key custody and independent recovery remain mandatory acceptance gates.


## 2026-11-21 — D-496 key destination directory-swap race

The D-495 parent-symlink preflight was not atomic with final key file creation. `tests/test_hosted_storage.py::test_private_key_output_parent_swap_cannot_redirect_secret` injects a rename+symlink redirect after directory validation for both key commands; original implementation wrote its fresh key into the redirected folder in isolated reproduction. POSIX path traversal now uses directory handles and `open(..., dir_fd=parent_fd)` with `O_NOFOLLOW` for each ancestor and the output filename. Expected acceptance: neither a pre-planted parent symlink nor a between-checks swap can send a generated key to the wrong directory; new files remain private mode 0600, existing filenames remain unmodified, redirected stdout never exposes a key. Evidence: c6ac720 test-first, adeb18f/7f182f3 implementation. These checks require full CI, exact-source Render QA and trusted operator path acceptance. The non-POSIX fallback remains preflight-only; select private trusted destinations. This is independent of, and does not replace, the real S3 backup and isolated PostgreSQL restore gate.
