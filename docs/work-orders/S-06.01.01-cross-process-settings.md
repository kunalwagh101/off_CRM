# Work order — S-06.01.01 cross-process workspace settings serialization

## ID
S-06.01.01 — Workspaces with their own keys and logins. CHECK-mode defect repair.

## GOAL
Concurrent server processes updating different workspaces must not erase each
other's AI provider settings or encrypted provider keys.

## BLAST RADIUS / CONSUMERS
The shared WorkspaceAISettingsStore is consumed by:
- API connector/settings routes in api/app.py (connect, disconnect, overrides,
  mailbox unlock, workspace settings, provider description/discovery);
- AgentRoutineExecutor for workspace-bound egress settings/credentials;
- MeetingTranscriber for workspace-bound egress settings/credentials;
- every API AI/image/transcription path that resolves a workspace-bound broker.

Public read semantics stay unchanged. This work changes write serialization only.

## ROOT CAUSE
Each WorkspaceAISettingsStore instance owns its own threading.RLock. Two server
processes (or two independent store instances) can both read the same JSON/key
document, then atomically replace it. Atomic replace prevents partial files; it
does not prevent lost updates.

## TEST
Create two independent WorkspaceAISettingsStore objects pointing at the same
data directory. Force their pre-fix read/modify/write windows to overlap, then
connect a provider/key in workspace alpha and beta concurrently.

After both calls:
- alpha settings still exist;
- beta settings still exist;
- alpha resolves only alpha's stored key;
- beta resolves only beta's stored key.

The test must exercise independent store instances, not one shared object.

## FIX
Serialize read-modify-replace writes across processes with a small standard-
library lock local to WorkspaceAISettingsStore. Keep atomic replace for crash
safety. The lock must cover the whole read-modify-write window for:
- settings patch/save;
- connect/disconnect provider;
- overrides/mailbox unlock;
- encrypted key read-modify-write.

Do not change read-only methods or public method signatures.
