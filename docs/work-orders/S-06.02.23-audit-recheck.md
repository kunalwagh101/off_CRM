## PROCEDURE — per finding
1. Read its section under "Detailed findings". Write its reproduction as a
   test against `develop`, in the file that already tests that area (search
   `tests/` for the module). Use the application's real entry point — the API
   through `TestClient`, a CLI's `main`, a store's public methods — not private
   helpers.
2. Run it.
   - **It passes** (the finding no longer holds): keep the test. It is now the
     regression test; name it after the behaviour, and put `A<nn>` in its
     docstring.
   - **It fails** (the finding still holds): do not commit a failing test.
     Add a `DEFECT_LOG.md` row (`open`), and a story in `PRODUCT_BACKLOG.md` —
     or a work order under an existing story — whose first step is this test,
     red. Keep the test in the work order's text.
3. Add a status column to the audit's "Findings at a glance" table: closed
   (with the test's name) or open (with the `D-nnn`). The table must stay
   readable as the audit's summary.
4. A finding that is a product gap rather than a bug — A27, A28, A29 — is
   answered with the story that owns it, not with a test.
