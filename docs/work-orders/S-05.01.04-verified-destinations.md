# S-05.01.04 — Public fetches use verified destinations

Status: BACKLOG. Existing prerequisite S-05.01.01 remains IN_REVIEW.

## User outcome
Public research fetches cannot access internal infrastructure if the hostname resolution changes after validation. Existing safe public discovery continues to work.

## Code and contract
Read `AGENTS.md`, `discovery.py`, `tests/test_discovery.py`, `tests/test_crawler_frontier.py`, A08 and D-267. The existing `SafePublicFetcher` checks the DNS results but its HTTP transport opens a separate connection. Make the validation apply to the *actual remote connection*, without weakening HTTPS certificate and hostname verification.

## Acceptance tests
- A controlled DNS-change test proves that the transport cannot connect to an unchecked destination.
- Redirects and reused connections still enforce public-network restrictions; a lookup or validation failure is an actionable refusal.
- A permitted public HTTP/HTTPS fixture still fetches successfully, with redirects, robots checks, limits and pacing unchanged.
- The JavaScript discovery path has equivalent destination protection; do not claim it safe from a test of the HTTP path alone.
