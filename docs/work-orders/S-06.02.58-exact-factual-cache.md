# S-06.02.58 — Exact factual response-cache eligibility (A12 / D-360)

Status: IN_REVIEW pending exact-source complete QA and release acceptance. Branch: `develop` only.

## User outcome
A changed source document or instruction cannot silently receive a stale answer because its words look similar. An identical request may still reuse its answer without a provider call.

## Contract and implementation
- Use the existing `ResponseCache` behind `EgressBroker.call`; preserve the allowlisted task types, data-class exclusions, workspace/policy isolation, TTL, statistics and durable SQLite schema.
- Only an **exact canonical payload identity** is eligible for factual reuse. Disable lexical Jaccard near-matching for all currently allowed factual tasks, even if the old constructor option `near_match=True` is supplied. Keep the option for API compatibility, not as a correctness bypass.
- Old indexed rows may remain until normal expiration/eviction, but their legacy partition keys must not be trusted by newly-scoped broker calls. No schema migration or destructive deletion.
- Different numbers, units, currency, negation, dates, company names or instructions must not reuse an old result. The original response must remain accessible only to its original exact request.
- The scanner and trust tier checks remain before cache access; never store mailbox data. No new provider egress.

## Test-first acceptance
- **RED:** old `tests/test_ai_cache_integrity.py` A12 numeric and negation inputs return an incorrect near hit.
- **GREEN:** those inputs miss and the identical source hits; existing exact-hit, expiry, workspace, policy and email non-cache regressions pass.
- Full SQLite and disposable PostgreSQL, frontend/build, Chromium, static audits, concurrency, traceability/board structural verifier via `Dockerfile.review` on exact source.
- Include negative security cases and restart safety; do not claim independent penetration certification based on unit tests.

## Operational notes and rollback
Stricter matching can increase provider usage and spend relative to historical near hits. Keep quotas and error messages visible. If rollback is considered, earlier near-cache reuse becomes possible again; do not enable legacy fuzzy matching for factual work until an equivalent correctness proof exists. No database schema or production data change is required.

**Release blockers:** independent penetration review, real model/customer acceptance, full-history board verifier and production deploy. Keep IN_REVIEW until those gates pass.
