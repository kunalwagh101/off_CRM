# S-03.01.03 / audit A07 — browser destination security (2026-10-13)

**Status: IN_REVIEW, incomplete security fix. Do not deploy as complete protection.** Branch develop.

## What was implemented
- `browser/policy.py` rejects private, loopback, reserved, link-local and non-global IPv4/IPv6 literals; noncanonical numeric representations (such as `127.1`, `0x7f000001`, `2130706433`); local DNS suffixes; malformed web requests with no hostname.
- `tests/test_browser_agent.py` exercises the policy in attended and unattended modes with private IPs, local hostnames and permitted public destinations.
- `tests/test_browser_box.py` checks browser RequestGuard verdicts on private redirect/subresource target URLs, even with an explicit unattended host allow-list.

## Verification actually executed
An isolated Python host-classification smoke case passed: 13 non-public representations blocked, 3 public addresses/domains allowed. These were hand-extracted logic checks, **not** the repository pytest suite or an actual browser connection test.

## Unresolved high-severity bypass
**A network-level boundary is still missing.** The Docker browser currently uses a general `--network=bridge` network. Its CDP request guard sees hostnames before dispatch, but a public-looking hostname can resolve or rebind to a private address *after* that decision. A policy-only fix does not prevent internal connections from the Chrome networking process. The box must use a controlled egress gateway / network policy that checks actual destination IPs; otherwise disable browsing in sensitive deployments. Before DONE, prove forbidden endpoints have zero received connections across navigation, redirects, background requests, new tabs and attended/unattended sessions. A successful policy verdict test is insufficient.

## 2026-10-13 — production bridge fail-closed containment (DD-91)
`BrowserBox.policy()` and `BrowserBox.command()` now refuse to prepare unrestricted Docker-bridge networking with `OFFSETX_PRODUCTION=1` (also true/yes/on); `describe()` reports `available: false` and the same actionable isolation message. This prevents off_CRM from launching its BrowserBox network path in declared production mode while the DNS-rebinding gap remains. Local/nonproduction launches intentionally retain the existing bridge behaviour, which is **not** safe against DNS rebinding. This does not control the owner's separately attached host Chrome browser.

Added `tests/test_browser_box.py::test_production_browser_refuses_unrestricted_docker_bridge` and `test_local_browser_still_builds_its_existing_command`. **Tests committed but not run in full repository**; no Docker/Chromium zero-connection proof, no production deployment. The requirement to deliver useful public browsing with a verified IP egress boundary remains unmet, so this story remains **IN_REVIEW**. Reversal without a verified alternative would restore the vulnerability; rollback should leave production browsing unavailable.
