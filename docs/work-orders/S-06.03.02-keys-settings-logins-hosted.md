# Work order — S-06.03.02 keys, settings and logins live in the hosted database

## ID
S-06.03.02. Feature `F-06.03`, phase 1. Decisions `DD-66` (amended
2026-10-02), `DD-69`, `DD-70`. Size L. Depends on `S-06.03.01` and
`S-06.02.31`.

## GOAL
With `OFFSETX_DATABASE_URL` and `OFFSETX_SECRETS_KEY` set once, a provider key
typed in Connectors, each workspace's AI settings and limits, trust changes and
their history, the spend and call counters, workspace logins and the egress log
all survive the app's disk being wiped — on any PostgreSQL 13 or newer: Render
or Neon now, AWS or Azure later (the owner, 2026-10-02). A missing, malformed
or wrong secrets key stops the start with a sentence. With no
`OFFSETX_DATABASE_URL`, nothing changes.

## DESIGN
- `db/hosted.py` — `OFFSETX_SECRETS_KEY`; `HostedStorageError`, a sentence for
  the operator; `DocumentTable`: named documents in `offcrm_documents`, opened
  lazily like `EgressLog` so a close and reopen is safe, written under an
  exclusive transaction (`pg_advisory_xact_lock` on PostgreSQL, `BEGIN
  IMMEDIATE` on SQLite); the secrets-key check document, so a wrong key is
  caught even before any key is stored.
- `db/schema.py` — `offcrm_schema(component, version)` and forward-only steps,
  applied under the same lock, so two instances starting together cannot both
  migrate and a database moved between hosts is upgraded from where it is.
- `db/connection.py::PostgresDatabase` — a connection idle 30 s or more is
  checked before use and reopened if the server dropped it; one that failed is
  reopened before the next statement. A failed statement is never re-sent.
  No server-side prepared statements, so a pooled URL works.
- `ai/workspace.py` — the settings document and the encrypted keys go through a
  vault: the files of today, or the documents `ai_workspaces` and
  `ai_provider_keys`, encrypted with `OFFSETX_SECRETS_KEY`, which is never
  written anywhere.
- `ai/quota.py` — the counters in the document `ai_quota` when hosted (`DD-69`).
- `api/auth.py` — the logins' SQL through one shared connection when hosted
  (`BYTEA`, `BIGINT` there); SQLite per call, as today, when not.
- `privacy.py` — the workspace-account adapter reads and deletes through the
  login store, so a privacy request reaches hosted logins.
- `api/config.py` — `secrets_key`; a URL without a key, a key without a URL and
  a key that is not a key are refused with the next step.
- `api/app.py` — hosted storage opened and the key checked in `create_app`,
  before anything is served; readiness probes it; local backup stays refused.
- `ai/eval_cli.py` — the same stores as the app when the URL is set.
- `db_cli.py` — `offsetx-db new-secrets-key`; `offsetx-db forget-provider-keys
  --yes` for a lost key: it clears the stored keys and the check, and each
  workspace pastes its keys again.

## BLAST RADIUS
- `WorkspaceAISettingsStore`: every AI route, the broker's credential
  resolver, routines, meetings, the eval tool.
- `QuotaTracker`: the broker's limit check, the usage numbers on Connectors.
- `WorkspaceAuthStore`: login, the session check on every request, workspace
  administration, the privacy service.
- `PostgresDatabase`: the egress log, video and GTM stores already on it.
- Backup and restore: refused while any store is hosted, unchanged.
- Suite before: 2501 passed, 0 failed, plus the four inventory tests.

## TEST (write first, watch it fail)
Over SQLite-as-the-URL always, and PostgreSQL when `OFF_CRM_TEST_POSTGRES_URL`
is set:
1. A key, limits, a trust raise with its reason, a second login, the counters
   and an egress row written by one app are all read by a second app on an
   empty data folder with the same two settings — and none of those stores left
   a file in either data folder.
2. The database holds the key only as ciphertext that `OFFSETX_SECRETS_KEY`
   opens.
3. A URL without a key, a key without a URL, and a malformed key are refused
   with a sentence naming the setting and the next step.
4. A different key on the same database is refused at start — with keys stored,
   and before any are.
5. Two writers of the settings at once lose neither change.
6. PostgreSQL: a connection the server dropped is reopened, and a statement
   that failed is not re-sent; a schema already at its version is not migrated
   again.
7. A privacy request finds and deletes a hosted login.
8. `new-secrets-key` prints a key the app accepts; `forget-provider-keys`
   refuses without `--yes` and with it lets a different key start.
9. With no URL, every store is the file it was.

## DONE WHEN
The tests pass on both backends; the whole suite is green; a real app process
configured in the browser is stopped, its data folder deleted, and a new
process on an empty folder with only the two settings shows the key, limits,
trust, logins and egress log; a fresh-context review's findings are fixed or
filed.
