# S-06.02.64 — Writable restricted sandbox outputs (A32 / D-121)

Status: BACKLOG, owner-authorised test-first build-ahead; audit S-06.02.23 remains IN_PROGRESS.
Branch: develop only.

## User outcome
A sandbox job uses the existing non-root UID/GID 65534 container and produces files under the *only* writable mount, `/work`. No broader host filesystem access, privileged container, network access, or secret visibility is allowed.

## Existing contract
`offsetx_apollo_builder/ai/sandbox.py` creates host-owned 0755 folders, but `SandboxPolicy.docker_command` runs as 65534:65534. A32 showed EACCES on /work in an actual Docker job. `/inbox` is a read-only mount and `store` must be completely absent from the mount list.

## Acceptance (test-first)
1. Newly created and legacy work directories permit UID 65534 to write when mounted directly as /work; host parent remains mode 0700.
2. Never relax container user, sandbox flags, storage mounts or networking to make writes succeed.
3. Refuse symlinked job roots, inbox or work directories before applying permissions; do not chmod an external target.
4. Execute a genuine POSIX UID-65534 subprocess write probe (not a mock), and an independent real Docker write with pre-pulled pinned image (separately required before DONE).
5. Run existing sandbox isolation, egress, budget tests; full Python/PG/Chromium/Node and board verifier; document rollback.

## Recovery and limitations
The job root must remain private. A sticky writable /work folder is safe only behind the private parent: a direct Docker bind mount bypasses the parent, and the worker runs as non-root. Every job has its own work root; this does not authorise sharing it between untrusted jobs. Roll back by pausing sandbox execution before reverting the permissions repair. An actual Docker engine under a native Linux host and independent attack testing remain release gates.
