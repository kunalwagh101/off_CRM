# S-06.02.51 — Protect video uploads before multipart parsing (A15)

**Feature:** F-06.02 production reliability. **Status:** IN_REVIEW, verification required. Branch: develop.

## Why this follows S-06.02.50
S-06.02.50 was tested on Render (2766 SQLite / 2786 PostgreSQL) and limits endpoint \`UploadFile.read(limit+1)\`. Starlette has already parsed and possibly spooled the entire request before that handler runs. The remaining A15 attack is request-stream resource exhaustion.

## User-visible outcome
Upload endpoints return HTTP 413 on oversized bodies, HTTP 408 on a stalled sender and HTTP 429 if all video upload slots on a web worker are occupied. Their existing per-file 413 remains a second defense. Normal imports and renders still use the same URLs and database records.

## Scope and contracts
- Exact POST routes: \`/api/v1/campaigns/{id}/video-media\`, \`/api/v1/video-projects/{id}/renders\`. Other endpoints are not changed.
- Content-Length is a fast-rejection hint only. Count actual received bytes; reject at \`OFFSETX_MAX_UPLOAD_BYTES + 16 KiB multipart overhead\`, including chunked and forged small headers.
- Bounded spool keeps first 256 KiB in memory then rolls to a private temporary file; always closes on success/disconnect/error/cancellation.
- Two in-flight uploads per worker and a bounded 50 ms acquisition window, returning HTTP 429 rather than queuing indefinitely. 30-second idle timeout returns HTTP 408.
- Keep existing authentication/authorization, header safety and file gates. Never log media or secrets.

## Test-first evidence
- Local independent FastAPI/ASGI prototype: first RED at missing guard import, then initial 7 cases GREEN; expanded 11 cases after fixing an ASGI test harness (awaitable send), **11 passed**. This is not off_CRM end-to-end proof.
- \`tests/test_video_upload_body_guard.py\`: authenticated real application POST coverage, early rejection, forged Content-Length, small valid imports, chunked early abort, per-worker concurrency, idle timeout, disk-rollover and disconnect cleanup.
- \`tests/test_video_upload_security.py\` prior tests must remain green.
- Required Render QA gates: \`uv run pytest tests/test_video_upload_body_guard.py tests/test_video_upload_security.py -q\`; \`uv run pytest -q\` SQLite and disposable PostgreSQL; existing frontend/npm audits and Chromium; Ruff; full-history board verifier where available.

## Operational limitations
The cap is **per web worker**. Reverse-proxy and multiple-process/global quotas, live network timing and measured pressure under real concurrent uploads, valid content duration/codec resource limits, and production disk alarm thresholds need separate acceptance. Disk spool uses the OS temporary directory and automatically unlinks it; keep at least \`2 * (MAX_UPLOAD + 16KiB)\` free temporary space per worker. No schema or worker change. The rollback is to revert this ASGI guard only, retaining endpoint size checks, but doing so reopens pre-parser exposure; safer rollback is a patched version or front-proxy upload cap.

No mark DONE until execution and operational evidence is attached. A15 remains open if independent pressure tests or multi-instance quotas are unproven.
