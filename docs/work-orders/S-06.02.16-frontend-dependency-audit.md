# Work order — S-06.02.16 frontend dependency audit

Task role: security/build engineer; branch: develop. No owner decision or upstream dependency.

## Contract
A clean npm ci in frontend must run two registry-backed checks: production dependency vulnerabilities at every severity (npm audit --omit=dev --audit-level=low) and development tree at high/critical threshold (npm audit --audit-level=high). Both must be hard CI gates, not advisory output masked by `|| true`. A breaking upgrade requires a regenerated lockfile with matching package.json plus frontend tests and production build, not a guessed hand edit.

## Initial evidence
Current frontend manifests declare React 19.2.7, Vite 8.1.4, Vitest 4.1.10, TypeScript 7.0.2, @vitejs/plugin-react 6.0.3. A registry-backed `npm audit` and `npm ci` could not execute here because the container has no DNS for registry.npmjs.org; GitHub Actions runners also fail before allocation. Snyk's per-package listings and Vite advisories provide context, not a full lockfile audit and not evidence of zero transitive high-severity findings.

## Implementation and acceptance
1. Add hard audit gates to the existing CI quality job after npm ci, before Python and frontend tests.
2. Tests in tests/test_ci_verifier_environment.py assert that both jobs are present, use correct thresholds, have no output-swallowing shell operators, and run after npm ci.
3. Run npm ci, npm audit --omit=dev --audit-level=low, npm audit --audit-level=high, npm test, npm run build in frontend; remediate any findings with supported upgrades, regenerate lockfile using npm, inspect diff, and rerun. Do not claim npm audit passed until it really does.
4. Execute full board verifier; review history and rollback with a previous locked manifest pair.

Risk: once CI runners are restored, a high finding may block merging rather than silently pass. That is deliberate.
