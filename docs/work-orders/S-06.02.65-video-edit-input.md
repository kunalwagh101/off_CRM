# S-06.02.65 — Strict nested video-edit request validation (A22)

Status: BACKLOG until the review; owner-authorised test-first build-ahead on `develop` while S-06.02.23 stays IN_PROGRESS.

## Problem
The API route `POST /api/v1/video-projects/{project_id}/edit` uses `VideoEditBody`, but its `operations` array is typed as `list[dict[str, Any]]`. Wrong nested `params` types reach `edits.apply(...).items()`, causing a 500, and unexpected nested keys or simultaneous batch+single edits can silently succeed. Audit A22 previously found the same class of unsafe write-body conversion, though the old image width bug was already typed.

## Acceptance
1. Invalid nested operation shape, non-object parameters, extra fields, two operation aliases or a simultaneous top-level single and batch return client 4xx without mutating the project, including a later invalid item in a batch.
2. Bounded batch count and per-edit text; no raw submitted value or stack trace in client errors.
3. Valid single and batch still save versions correctly and support undo after reopen.
4. Existing editor and API tests remain green; full SQLite/PG, frontend, Chromium, security and structural verifier gates run against exact source.

## Implementation boundaries
Prefer nested StrictModel/Pydantic validation before loading the project. Do not invent a second video engine, silently sanitize invalid edits, or change frontend flows. Keep edit operation aliases for existing clients. Preserve in-memory validation before database save. This is a limited remediation slice; it does **not** certify every A22 write endpoint.

## RED and GREEN
Run `uv run pytest -q tests/test_video_edit_validation_a22.py` on test-only source first, then implement. Test-only RED and green evidence are recorded in this file and `docs/evidence/2026-11-04-a22-video-edit-validation.md`.

## Rollback and release
No schema migration. A rollback must retain valid existing video projects and restore previous source if needed, but it reopens malformed nested input behaviour. Complete native request fuzzing, independent penetration, historical verifier and customer-production acceptance are separate conditions for DONE. `main` is untouched.
