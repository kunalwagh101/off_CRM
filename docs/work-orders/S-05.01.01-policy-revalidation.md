## ID
S-05.01.01 — A crawler with a frontier, not a loop

## Goal
A persisted frontier row that the current public-URL policy now rejects must not block valid due work behind it. The rejected row must leave the active frontier and claim_due() must continue until it fills the requested number of valid claims or no valid due work remains.

## Acceptance test
Add a focused regression proving:
1. two due rows already exist in the persisted frontier;
2. the first row in scheduling order is now rejected by the current validator;
3. limit=1 still returns the valid due row behind it;
4. the rejected row is removed from the active frontier;
5. the valid row receives a lease.

## Fixed decisions
- A validator failure during claim is a deterministic current-policy rejection, not a transient fetch failure.
- The rejected row is deleted transactionally. If policy later permits it again, a future seed/link may re-admit it normally.
- claim_due() keeps selecting after removing invalid rows so invalid persisted state cannot consume the caller's claim limit.
- No new dependency, queue, tombstone table, or schema migration.
