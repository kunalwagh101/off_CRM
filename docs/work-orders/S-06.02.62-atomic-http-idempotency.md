# S-06.02.62 — Atomic HTTP idempotency (A14 / D-364)

Status: BACKLOG; code built ahead under owner direction while S-06.02.23 audit remains IN_PROGRESS. Branch: develop only.

## Problem and evidence
The generic API `_idempotent` used cache lookup, operation execution and an upsert as separate steps. A14 (7 September audit) reproduced two duplicate campaigns under one key. On current develop, RED test-only source `ac10fa0`, isolated Render `dep-dblfslqjnfac73ft665g`, reproduced **five** failures at the actual HTTP entry point: two independent app instances, changed-payload replay, rollback failure, uncertain external send and malformed key.

## User outcomes and acceptance
1. Same key + canonical payload + principal through two separately opened FastAPI instances yields exactly one CRM mutation and stable 201 replay. Test against local SQLite and disposable PostgreSQL.
2. Same key with changed payload or different authenticated principal returns 409 without revealing prior response. Invalid/unbounded key returns 422 before mutation.
3. If a purely database mutation raises or the process crashes before commit, rollback its effect and result together. The retried request can safely create exactly one record.
4. External provider/Gmail operations may have an unknown send outcome. Commit an **in-progress** idempotency claim before transport; never retry automatically after ambiguous failure/crash. A completed result replays without invoking provider again.
5. Unverified pre-migration idempotency rows are refused, not silently treated as a trusted replay. No raw request body, credential, or caller identity must enter a non-secret-safe error.
6. Cross-worker PostgreSQL and local process concurrency, restart/recovery and rollback probes pass. Full SQLite/PG, API auth, egress/SES, frontend, Chromium, Ruff and board verifier gates pass on the exact source.

## Implementation boundaries
Reuse existing `OutreachStore.transaction(immediate=True)`: on PostgreSQL it takes a real transaction advisory lock, on SQLite an OS-backed write transaction. Pure CRM mutation, result and its key must commit together. For external calls reserve the key first, release DB lock, execute, then record the result; a crash leaves a refused in-progress request until reconciled. No automatic clear of in-progress records. Fingerprint request payload and authenticated principal (not the secret token). No migration: the old table still exists, but new records use a versioned response envelope. Legacy rows have no fingerprint and must refuse replay.

## Error and recovery
409 conflict means the prior key belongs to another request, an old unverified row, or an unresolved action; the client must NOT automatically change keys and retry external side effects. Operators reconcile provider receipts and stored records first. Never delete an in-progress row to bypass an uncertain send. On rollback keep the CRM and idempotency table together and stop old workers; the historical non-atomic helper would reopen A14.
