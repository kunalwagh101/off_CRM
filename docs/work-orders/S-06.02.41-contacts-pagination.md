# S-06.02.41 — Contacts pagination (audit A23 / D-271)

**Status: IN_REVIEW, no frontend execution proof.** Role: senior frontend engineer. Branch: develop.

## Existing user path and gap
The Contacts screen requests `limit=500` and never exposes the remaining rows. The authenticated API already accepts `limit` (1–500), `offset` and search/status filters and returns `total`. Reuse that contract, do not add a second endpoint or client-only pagination.

## Acceptance
- Every contact in a campaign can be reached in page-sized batches, including rows 501+.
- Search/status changes return to page one. Changing campaigns remounts the screen as the App already does.
- Accessible next/previous buttons, visible range/total and accurate disabled states. Keep edit/import/reload on the selected campaign and page.
- A page whose total shrinks out from under it returns to the last existing page rather than trapping the user on an empty page.

## Implementation
`frontend/src/pages/Contacts.tsx`: 100-row server pages, offset and encoded filters; compact range and accessible page navigation. `frontend/src/pages/Contacts.pagination.test.tsx`: range/bounds, URL and rendered control checks. Production API and store paging logic are reused unchanged.

```bash
cd frontend && npm ci && npm test && npm run build
cd .. && uv run pytest -q && uv run python scripts/verify_board.py
```
Also manually test at least 501 persisted contacts in Chromium, across search/filter/campaign change, edit and import. Include screen reader tab/announcement checks. No schema migration. Rollback the frontend component only; the API's existing paging contract remains.
