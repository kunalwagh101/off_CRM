# S-05.01.04 / audit A08 — verified crawler destinations (2026-10-13)

**Status: IN_REVIEW, not DONE or deployed.**

## Implementation committed to develop
- `discovery.py` now returns a verified globally routable address from each preflight DNS check and uses `_PinnedPublicAdapter` for actual Requests TCP connections. The connection uses a numeric approved IP; HTTP Host, HTTPS SNI and certificate hostname stay the original URL hostname. Adapter is per request, there are no automatic redirects, and session-level proxy/custom transports are refused to avoid bypassing pinning.
- Existing explicit redirect validation, robots check, pacing, size and content-type checks remain in place. Browser-rendering/Crawl4AI is a separate engine and **is not yet protected against resolver-to-connection DNS rebinding**.
- `tests/test_discovery.py` adds a real local HTTP server with an injected resolver simulating an approved global address, asserts socket creation uses that address and Host is preserved; rejects a private DNS answer before any socket; checks HTTPS Host/SNI property and proxy refusal.

## Verification actually run — isolated, not the repository test suite
- A standalone Python Requests+urllib3 HTTP server test passed: a socket request for `outside.example` connected using the approved `93.184.216.34` argument while serving from an isolated local test server. The Host header stayed `outside.example`.
- A second standalone SSL/TLS fixture generated its own certificate for `outside.example`, sent a real local HTTPS request through the pinned adapter with certificate verification enabled, and passed: socket target `93.184.216.34:443`, Host `outside.example`, successful certificate verification and response.
- These are isolated source-equivalent harness checks only. A private GitHub checkout was not executable in the shell; no full Python, Chromium or database tests ran.

## Outstanding blockers before DONE
1. **Crawl4AI route interception is still racy**: it checks DNS separately and uses a browser connection afterwards. Require an actual egress firewall/network gateway that verifies final destination IP for every browser request, including redirects, WebSockets, subresources and new contexts.
2. Run targeted `uv run pytest tests/test_discovery.py tests/test_crawler_frontier.py -q`, full `uv run pytest -q`, `uv run python scripts/verify_board.py`, and code review in a working repository environment.
3. Run controlled DNS-rebinding integration with a live public fixture and private test service and prove **zero private connections**; run HTTPS certificate mismatch, robots pacing and redirects end-to-end. CI currently fails before running steps.
4. Dependency `S-05.01.01` remains IN_REVIEW and must be DONE before this story can move to DONE.

## Rollback
Revert the per-request pinned transport commits after a targeted validation failure. If reverting removes destination integrity, **disable the affected automated crawling capability** until a verified transport/network boundary is restored. No data migration or customer data changed.
