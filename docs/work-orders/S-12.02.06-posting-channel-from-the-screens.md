# Work order — S-12.02.06 a plan's posting channel runs from the screens

## ID
S-12.02.06 — A plan's posting channel runs from the screens. Board: BACKLOG
(pullable: `S-12.02.02` is DONE). Fixes `D-82` and `D-97`; `D-87`'s part is
already done. Size M. Epic E-12.

## GOAL
A plan with a views goal reaches a published post without the owner writing
campaign ids into an API call: Apply pairs the posting and picture campaigns,
the owner approves or skips drafted posts on Posting, and the plan's
posts-a-day is the rate that actually posts.

## BLAST RADIUS / CONSUMERS
- `offsetx_apollo_builder/gtm/service.py` — `apply_plan` / `_apply_channel`
  create the posting (distribution) and picture (image) campaigns, paused; the
  links carry `plan_id` and `channel`. Nothing pairs them today (`D-82`).
- `offsetx_apollo_builder/distribution/automation.py` — the content timer.
  Its config: `pipelines`, a list of `{distribution_campaign_id,
  image_campaign_id, angle, account_ids}`, and **one global** `posts_per_day`
  (default 1.0, capped by `pacing.MAX_PER_DAY`). Enabling needs at least one
  pipeline. Paused campaigns make nothing (`D-87`).
- `api/app.py` — `PATCH /content-automation` and
  `POST /content-automation/run` are **owner-only** (`D-125`, DD-59): the
  timer runs as the install, on the owner's keys. `GET /campaigns/{id}/posts`,
  `POST /posts/{id}/approve` and `POST /posts/{id}/schedule` exist; there is no
  skip.
- `distribution/engine.py` — `approve`, `schedule`; post statuses are `draft`,
  `approved`, `scheduled`, `published`, `failed`.
- `frontend/src/pages/Posting.tsx` — shows accounts, pacing and the automation
  mode; it lists no posts and approves nothing.

## DESIGN
1. **Apply pairs the campaigns** — through the content automation service
   object, not its HTTP route. The GTM service is handed a function that
   *adds* a pipeline, merging with those already declared (never replacing
   the list), with `angle` left empty — the timer's `angle_resolver` already
   reads the plan's angle at run time.
   **Only for the install's own workspace, `local`.** The timer spends the
   owner's keys; pairing another workspace's plan into it would reopen what
   `D-125` closed. A plan applied from another workspace gets a next step that
   says pairing needs the install owner — until timers run per workspace
   (`docs/architecture/CRM_TENANCY.md`, phase 4).
2. **Nothing starts at Apply.** The campaigns stay paused and automation is not
   switched on. Posting shows the plan's pair and one owner action, "Start
   posting for this plan": it resumes the two campaigns and enables the timer.
3. **Approve or skip on Posting.** A "Drafted posts" panel lists
   `GET /campaigns/{id}/posts` with status `draft` for the selected posting
   campaign, each with Approve (`POST /posts/{id}/approve`) and Skip — a new
   `POST /posts/{id}/skip` that sets a new status, `skipped`, which
   `publish_due` never publishes. Approval is still required before anything
   can be scheduled; that rule does not change.
4. **The plan's rate is the rate.** A pipeline gains an optional
   `posts_per_day`. When present, it is the pacer's starting rate for that pair;
   when absent, the global rate applies, as today. Apply writes the plan's
   posts-a-day into it (`D-97`).

## TEST (write each first, watch it fail)
1. `tests/test_gtm_apply.py`: applying a plan with posting and picture channels as
   `local` declares exactly one new pipeline for that pair and keeps the pairs
   already there; as another workspace it declares none and returns the next
   step naming the owner.
2. `tests/test_content_automation.py`: a pair whose campaigns are active, with
   automation enabled, drafts on a cycle (fake pipeline factory); the same pair
   paused drafts nothing (the `D-87` guard still holds).
3. The skip route: a skipped post is never published by `publish_due`; skip
   answers 404 for a post in a campaign the caller cannot see.
4. The rate: a pipeline with `posts_per_day: 3` starts its pacer at 3; one
   without starts at the global rate.
5. `frontend/src/components.test.tsx`: `DraftedPosts` renders each post with
   Approve and Skip, and an empty list offers the next step, not a blank.
