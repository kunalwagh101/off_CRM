# Branches: two, and where everything went

**The rule.** This repository has two branches.

| Branch | What it is | Render service |
|---|---|---|
| `develop` | Where every change lands first. The newest code, always. | `off-crm-develop` |
| `main` | What has been checked on `develop` and promoted. | `off-crm-demo` |

Nothing else is kept. A change is committed and pushed to `develop`. When
`develop` has been checked — the suites below pass and someone has used it on
`off-crm-develop` — `develop` is merged into `main`, which deploys
`off-crm-demo`. No story branches, no batch branches, no session branches.

Before 2026-09-23 there were 46 branches. Three lines had built the same
stories in parallel, two of them reusing the same ID numbers, and the newest
line had never run its own tests. This page is the record of how they became
one, so nothing has to be rediscovered.

## Working on `develop`

```bash
git checkout develop
git pull origin develop
# … change, then the checks every push must pass:
uv sync --extra dev --extra email --extra postgres --locked
uv run ruff check --select E9,F63,F7,F82 .
uv run pytest -q
(cd frontend && npm ci && npm test && npm run build)
uv run python scripts/verify_board.py
git push origin develop
```

`verify_board.py` without `--skip-tests` re-runs every DONE story's evidence
command, which is the check to run before promoting to `main`.

**Promoting to `main`.** Only after the checks above pass on `develop` and the
change has been seen working on `off-crm-develop`:

```bash
git checkout main && git pull origin main
git merge --no-ff develop
git push origin main          # this deploys off-crm-demo
```

Never rewrite `develop` or `main` (no force-push). A mistake is fixed by a new
commit, or undone with `git revert`, so everyone's copy stays valid.

## Render

`render.yaml` is a Blueprint with both services. Render builds each one from
the repository's `Dockerfile`, on its own branch, and checks
`/health/ready` before sending it traffic.

**Both services are on the free plan, and on the free plan everything under
`/tmp` is wiped on every restart and every deploy.** That is where both keep
their data today. Treat both as demos: nothing typed into either survives the
next push. This is deliberate — a persistent disk needs a paid service
([Render: disks](https://render.com/docs/disks)), and paying is the owner's
decision (`OPEN_QUESTIONS.md` Q-26), not something a merge should do.

Both deploy on every commit (`autoDeployTrigger: commit`). The safer setting,
`checksPass`, waits for CI; CI cannot start a runner on this repository today
(`D-75`), so it would mean never deploying. Switch it once CI runs.

On each service, set in the Render dashboard (they are `sync: false`):
`OFFSETX_ALLOWED_HOSTS` — the service's own hostname, for example
`off-crm-develop.onrender.com` — and `OFFSETX_DEMO_USERNAME` /
`OFFSETX_DEMO_PASSWORD` (12 characters or more). `OFFSETX_SESSION_SECRET` and
`OFFSETX_UNSUBSCRIBE_SECRET` are generated by Render.

To keep provider keys, AI settings, usage counters and logins across deploys,
also set `OFFSETX_DATABASE_URL` and `OFFSETX_SECRETS_KEY`
(`docs/architecture/HOSTED_STORAGE.md`, "Switching it on"). Each service gets
its own database: `develop` runs code nobody has reviewed yet, and must never
touch `main`'s keys or logins. Render's free database is deleted after 30 days
plus 14 days' grace, and Render allows one free database per workspace — so
the free option for two services is Neon.

### Making `main` keep its data

When real records go into `main`, change the `off-crm-demo` service in
`render.yaml` to a paid plan with a disk, and turn production mode on:

```yaml
    plan: 1c-2g              # a paid instance type (disks need one); 2 GB leaves
                             # room for the 64 MiB backup's in-memory buffers
    numInstances: 1          # one instance per disk — SQLite is not shared
    disk:
      name: off-crm-data
      mountPath: /var/lib/offcrm
      sizeGB: 10
    envVars:
      - key: OFFSETX_PRODUCTION
        value: "1"
      - key: OFFSETX_PERSISTENT_MOUNT
        value: /var/lib/offcrm
      - key: OFFSETX_DATA_DIR
        value: /var/lib/offcrm/local_data
      - key: OFFSETX_OUTREACH_DB
        value: /var/lib/offcrm/local_data/offsetx_outreach.db
      # …plus the existing ALLOWED_HOSTS, DEMO_* and SESSION_* keys
```

With `OFFSETX_PRODUCTION=1` the app refuses to start if the disk is missing or
the data is under `/tmp`, rather than run and lose it. Backup, restore,
readiness and the restart behaviour are in
`docs/architecture/WP1_OPERATIONS.md`. The valid `plan` values are the
instance types in Render's [Blueprint spec](https://render.com/docs/blueprint-spec)
(`free`, `0.5c-512mb`, `1c-2g`, …, as listed there on 2026-09-23).

## What happened to every branch (2026-09-23)

**The last step is the owner's.** The old branches are still on GitHub. Each is
to be kept as a tag, `archive/<branch-name>`, and then deleted — and GitHub
refused both to the cloud session that built `develop` (HTTP 403: that session
may push commits, not tags or deletions). From a clone with push rights:

```bash
git checkout develop && git pull origin develop
bash scripts/archive_old_branches.sh            # tag every old branch, check each on GitHub; deletes nothing
bash scripts/archive_old_branches.sh --delete   # the same, then delete the branches
```

It deletes a branch only once its tag is confirmed on GitHub at the branch's
commit, and only if nobody has pushed to the branch since. Deleting a branch
closes any pull request opened from it: 19 pull requests are open on these
branches, and their pages stay readable. `S-06.02.19` is BLOCKED on this step.

After it, each old branch can be recovered exactly as it was:

```bash
git fetch origin 'refs/tags/archive/*:refs/tags/archive/*'
git checkout -b look-at-it archive/feature/s-04-01-01-companions
```

Nothing is lost meanwhile, or even if the tags were never made: 22 of the 45
branches end inside `develop`'s own history; 20 more are kept by GitHub under
their pull request (`git fetch origin pull/14/head`); three have commits
nowhere else — `agent/s-02-02-01-bounded-run-loop`,
`claude/abacus-ai-app-idea-t1mnja` and `claude/production-ai-system-design-6413s6`.

**The base.** `develop` started from `feature/next-three-batch-4`, the line
with the most built work (`main` plus the next-three batches). It was
consolidated in this order:

1. Renumbered two defects that clashed with the E-12 block.
