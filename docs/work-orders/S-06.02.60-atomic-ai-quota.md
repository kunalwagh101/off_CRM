# S-06.02.60 — Atomic AI quota reservations (A11 / D-362)

Status: BACKLOG. Do not pull while S-06.02.23 remains IN_PROGRESS.
Branch: develop only.

## Evidence and scope
The September A11 audit reproduced concurrent overuse. The current source still calls \`QuotaTracker.check\` in \`EgressBroker.plan\` before transport, then calls \`QuotaTracker.record\` after transport. Each uses a process-local lock; the hosted JSON document is read and replaced without an atomic reservation. A corrupt local file can reset counts. This is source-confirmed, not a new live penetration reproduction.

## User outcome
Per-minute, per-day and USD spending caps are enforced **before** provider I/O across threads, processes and restarts. Unknown billing cannot become an unmetered free call.

## Test-first acceptance
1. **Given** one remaining request, **when** two independently started broker workers race behind a test barrier, **then** only one gets a durable reservation and only one provider call starts. Repeat on disposable PostgreSQL and for minute and day limits.
2. **Given** a priced model close to a daily dollar cap, **when** two requests start concurrently, **then** conservative reservations prevent the second billable call. Provider receipts reconcile actual cost exactly once and failed/ambiguous calls remain accounted for.
3. **Given** a crash, failed database write, corrupt local file or reservation expiry, **when** the next worker resumes, **then** usage cannot silently reset and no uncertain external action is automatically repeated.
4. **Given** different workspaces/credentials, **when** budgets are enforced, **then** the correct account scope is used; shared provider quota is shared where needed, without disclosing other workspace data.
5. **Given** an unsafe ledger, **when** the request is denied, **then** the user gets an actionable error reference matching one secret-free structured log line.

## Implementation approach
Reuse existing broker, quotas, and hosted database boundary. Make reservation and reconciliation transactional and idempotent. A Python RLock, JSON file rename or read-then-write is not multi-process safety. Keep model-tier filtering and the single broker egress gate. Use the existing dependencies unless a reviewed addition is unavoidable. Decide the exact workspace vs provider-key budget identity before READY.

## Required gates
- TDD RED with real EgressBroker entry point, two independent processes, a synchronisation barrier and a controlled fake provider recording actual invocation count.
- TDD GREEN against disposable PostgreSQL with competing reservations, price reconciliation, crash/retry, corrupt-ledger refusal, multi-workspace isolation and failover.
- Unit tests, integration tests, controlled adversarial race/security probes, secret-safe logs, full SQLite/PostgreSQL regression, Ruff, real Chromium impact, full board verifier, rollback/recovery.
- Deploy only to isolated Render QA first; record actual results against a pinned source commit. Do not call independent penetration or real paid-provider acceptance complete based on synthetic tests.

## Release constraints
No customer send/model calls, production database mutation, or main promotion. Keep OPEN until demonstrated cross-process safety, rollback and owner acceptance.
