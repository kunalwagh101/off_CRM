## Reporting contract

A shared report_failure interface accepts an exception, a fixed operation
identifier, and optional route template, workspace identifier and existing
error ID. It returns the reference to display and emits exactly one failure
record for the operation, even when nested boundaries encounter that failure.
Settle its concrete signature and ownership after the consumer inventory;
outer request handling and inner worker handling must not duplicate entries.

Records are JSON lines on standard output with UTC time, error ID, operation,
route/command, workspace, exception classification and safe traceback frames.
Use route templates, not raw paths/query strings. Never collect request bodies,
headers, cookies, prompts, customer content, traceback locals or source lines.
Arbitrary exception messages can contain customer data: db.connection.redact
only masks a known database password and alone is not sufficient. Default to
safe exception classification and frame metadata; any message included needs
an explicit safe policy and tests. Do not dump environment variables or vaults
to discover secrets. Log IDs/counts instead of contents.

Keep compatible JSON detail responses for failed API calls, add an error_id
field and readable "Reference: E-..." text, and avoid exposing the raw exception.
Returned 5xx responses as well as raised exceptions require coverage. Known
failures retain an actionable next step. Commands and job status expose the
same ID without replacing correct exit codes or swallowing failure.

Local installs also write size-capped rotating files under
OFFSETX_DATA_DIR/logs. Hosted Render installs use standard output only. Verify
thread/process safety and bounded disk usage; do not introduce rotation races
between the web process and worker. Define behaviour for unavailable log files
and broken output streams; logging must not mask the original operation's
failure or turn a successful operation into a reported business failure.
Initialisation is repeatable and must not accumulate duplicate handlers.

Successful requests may produce only the bounded access record specified in
the story (method, route template, status, elapsed time), without request data.
Account for uvicorn's existing access/error logging so a second channel does
not leak data or duplicate failure records.

## Acceptance checks — write and observe RED before implementation

1. A real API request that raises unexpectedly, a handled provider/database
   failure, an explicit 5xx response and a session-lookup outage each return a
   readable detail and reference matched to exactly one JSON failure record.
   Successful requests and ordinary client refusals do not become failures.
2. Failed worker cycles, background jobs and installed commands expose the
   same reference as their record; existing retry, exit, approval and restore
   behaviours still hold. Parameterise installed command boundary coverage.
3. Messages containing credentials, cookies, customer text, prompts, URLs with
   encoded passwords and chained exceptions leave none in output, log files
   or user-facing generic failures. Exercise raw paths/query values as well.
4. Concurrent operations have distinct IDs; nested propagation emits once;
   repeat initialisation, multiple app instances and rotation cannot duplicate
   handlers or lose the required record. Confirm bounds with real local files.
5. Local logs survive a process restart, rotate within the documented cap and
   remain searchable by reference; Render mode writes no local log file.
6. File/output failure and shutdown/cancellation preserve the original result,
   safe reporting and appropriate exit status. Run a real app-process failure
   and an installed-command failure in a disposable data directory, matching
   each displayed ID to captured output. Simulated failures prove reporting,
   not a live provider integration or Render retention.
