# Work order — S-06.02.04 retry revalidation

## ID
S-06.02.04 — Data deletion and subject access. CHECK-mode defect repair.

## GOAL
A deletion retry must not report complete if a store that succeeded on an
earlier attempt has acquired new matching subject data before the retry.

- CRM-last retry ordering
- retention/legal-hold policy
- any unrelated store adapter

## INTERFACES
Keep these public signatures unchanged:

```python
class PrivacyAdapter(Protocol):
    name: str
    def find(self, subject: SubjectIdentity) -> list[PrivacyRecord]: ...
    def delete(self, subject: SubjectIdentity) -> dict[str, int]: ...

def PrivacyService.delete(
    self,
    request_id: str,
    subject: SubjectIdentity,
    *,
    confirmation: str,
) -> dict[str, Any]: ...
```

## TEST
Add a regression to `tests/test_privacy.py` using an adapter that:
1. contains one matching row on attempt one;
2. deletes successfully;
3. another adapter fails, leaving the request partial;
4. a new matching row is inserted into the already-successful adapter;
5. retry must re-delete that row before global completion;
6. a successful adapter with no reappeared data must still not receive a
   redundant second delete call.

## FIXED
- Prior success is reusable only after the adapter is re-inventoried and has no
  matching records now.
- A missing adapter or failed re-inventory is a failed store, never success.
- Re-inventory is read-only.
- CRM remains last.
- No new persistence or background reconciliation.
