# Hosted storage — data that survives a deploy on the free plan

**Status: design, not built.** Answers `Q-26` with the owner's choice of
2026-09-25: keep Render free, and keep the data in a free hosted PostgreSQL.
Stories: `S-06.03.01` to `S-06.03.05` (feature `F-06.03`). Decision: `DD-66`.

## Why

On Render's free plan the service's disk is `/tmp`, wiped on every deploy and
restart. Everything under `OFFSETX_DATA_DIR` goes with it: the CRM, the
encrypted provider keys **and the master key that decrypts them**
(`ai/workspace.py`, `.ai_master.key`), workspace logins, audit records. A key
the owner types into Connectors today is gone at the next push.

The owner's rule, which this design keeps: **a user adds provider keys in the
app, never in the server's environment.** Keys typed in the app must therefore
live somewhere a deploy does not touch.

## The one thing the operator sets once

A server that keeps its data elsewhere has to be told where. Two deployment
settings, set once when the install is created, like a house key:

| Setting | What | Who sets it |
|---|---|---|
| `OFFSETX_DATABASE_URL` | the hosted PostgreSQL address | the install owner, once |
| `OFFSETX_SECRETS_KEY` | the master key that encrypts every stored provider key | the install owner, once; generated by a command, never typed |

Neither is a provider key, and no user ever sees them. Every provider key is
still entered in the app, encrypted with the master key, and stored in the
database. A separate secret from `OFFSETX_SESSION_SECRET` on purpose: rotating
the login-signing key must not make every stored provider key unreadable.

## Which host

Any PostgreSQL URL works — the code must not care. The recommended free host is
**Neon**, checked on 2026-09-25 (`neon.com/docs/introduction/plans`):

| | Neon free | Supabase free |
|---|---|---|
| Storage | 0.5 GB per project | 500 MB |
| Idle | compute sleeps after 5 minutes, wakes on the next query | **the project is paused after a week without activity and must be unpaused by hand** |
| Restore history | 6 hours | none on free |

Supabase's pause is disqualifying for an app whose owner may not log in for a
week. Neon's limits are real and shape the design: 0.5 GB means files do not go
in the database, and a 6-hour restore window means Neon's history is not the
backup.

## What moves, in order — each phase green before the next

| Phase | Story | Moves | Proof |
|---|---|---|---|
| 0 | `S-06.03.01` | nothing — an inventory: every store, its backend today, its size on a real install | a test lists every store opened in `_open_runtime` and its backend; the doc's table is generated from it |
| 1 | `S-06.03.02` | provider keys (encrypted with `OFFSETX_SECRETS_KEY`), AI workspace settings, trust overrides, workspace logins, the egress log | a key typed in Connectors survives a real container being destroyed and recreated with only the two settings |
| 2 | `S-06.03.03` | the CRM store (`OutreachStore`, SQLite today, about 90 methods), with a copy tool from an existing SQLite file | the CRM suite runs against both backends; a real install's CRM copied across with counts reconciled |
| 3 | `S-06.03.04` | backups: a nightly encrypted export of the database, kept outside it; restore from it tested | an export restored into an empty database gives the same counts; the owner can download it |
| 4 | `S-06.03.05` | the production contract: `validate_storage` accepts the hosted topology and refuses a half-hosted one | production refuses to start with a hosted CRM but a local key vault, and the reverse |

**Files stay disposable until a later decision.** Media uploads, video files,
agent screenshots and exports are files, not rows, and 0.5 GB would not hold
them. On the free plan they are still lost on a deploy; the screens that hold
them must say so. Object storage is its own question, raised when phase 2 lands.

## What does not change

- The seam: stores already open their database through
  `db/connection.py::open_database`, and the egress log already runs on
  PostgreSQL (`docs/architecture/POSTGRES.md`). Phases 1 and 2 put more stores
  behind the same seam; no store learns which backend it has.
- The AI rules in `AGENTS.md`: the key vault moving to a database changes where
  ciphertext rests, not who may read it. No model gets a query path to it
  (rule 6).
- Local installs: with no `OFFSETX_DATABASE_URL`, everything stays in SQLite
  under `OFFSETX_DATA_DIR`, exactly as today.

## Risks

- **Compute hours.** 100 CU-hours a month is about 400 hours at the smallest
  size. The scheduled jobs keep the database awake while the service runs; on
  Render free the service itself sleeps when idle, which helps. Phase 1 records
  real usage for a week before phase 2 moves the CRM.
- **Latency.** Every query crosses the network; a cold database takes a moment
  to wake. Screens must show loading, never a blank.
- **Migration on live data.** Phase 2's copy tool is run on a copy of a real
  CRM first, with its inverse (back to SQLite) written and run once.
- **Two stores for one install during phase 1** (keys in the database, CRM
  still local and wiped): acceptable for the free demo, and the reason phase 4
  exists — production refuses the half state.

## Reversal cost

Expensive, not irreversible: PostgreSQL is PostgreSQL, so changing host is a
dump and a restore, and the SQLite path stays for local installs. The cost is
the work in phases 1–2 and the network dependency they add.
