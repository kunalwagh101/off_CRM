# S-06.02.67 — Restrict personal-data access and erasure to install owner (A24/A05)

Status: BACKLOG. Build-ahead security remediation while active S-06.02.23 audit remains IN_PROGRESS. Only develop. No DONE or production claim without acceptance.

## Existing user-visible workflow
`PrivacyService.for_local` already inventories 12 stores, supports subject access, confirmed preview, resumable delete, nonpersonal receipts and synthetic cross-store tests. Do not rebuild that code. The `/api/v1/privacy/{subject-access,deletion-preview,deletions/{request_id}}` routes currently authenticate but do not enforce an install-owner role. Ordinary workspace logins can request personal-data inventory and can preview or delete globally shared CRM contacts without install approval. The CRM has no final tenancy decision yet (Q-27), so a workspace label alone is not safe authority to erase contact rows.

## User outcome and acceptance
1. **Given** a signed-in ordinary workspace account, **when** it calls subject access, deletion preview, deletion execution or the destructive confirmation route, **then** the API refuses with 403 before reading personal data or changing any persistent store. It must not expose a subject's email/record content in the error.
2. **Given** install API token or a deliberately created install-owner login with `workspace_id=local`, **when** it accesses and confirms a deletion of a synthetic subject, **then** the supported route remains available and the subject's contact is removed, with a truthful receipt.
3. **Given** an owner-created preview/request id, **when** a nonowner attempts to execute/retry it (including spoofed workspace headers and body), **then** no delete happens, even if the caller knows confirmation phrase and request id. Owner can still finish and retry safely.
4. **Given** a rejected subject deletion or inventory, **when** the owner examines outcomes, **then** unrelated persons, other-workspace user accounts, and existing login sessions remain unchanged.
5. **Given** a backend restart or new TestClient, **when** the same restricted login reuses its session, **then** permissions remain enforced. No changes to live provider credentials or customer data.
