# OFF_AI zero-access security

## Governing invariant

Models never pull. OFF_CRM pushes.

An AI provider receives a constructed text packet and returns text. It receives no mailbox credential, provider-independent tool, CRM/database handle, file access, browser session, context-store query, retrieval function, or callback that can request additional owner data.

## Allowed egress

Only task-specific combinations of these fields can leave:

1. one target person's public professional information;
2. the owner-approved public OffsetX positioning line;
3. the owner's outbound template;
4. instructions generated by OFF_CRM code;
5. fully public, non-personal chat content for public tasks.

## Hard deny

- inbound or outbound mailbox content and received subjects;
- email addresses;
- Gmail tokens, provider keys, credentials, connection strings, or environment values;
- full contact lists or other POIs;
- CRM notes, deal data, projections, pipeline records, or sales data;
- context/memory/evidence/notebook records;
- local paths and files;
- owner identity beyond the approved positioning line.

## Trust enforcement

Two facts must pass: jurisdiction and data terms. `EgressPolicy.effective_tier()` also checks direct-versus-aggregator hosting and model provenance.

- Tier A needs acceptable jurisdiction, direct hosting, a terms-check date, and exact `no_training_no_retention` classification.
- Tier B receives public, non-personal work only.
- Tier C is forced for China-jurisdiction hosts, is off by default, requires explicit selection and task enablement, and cannot fail over.
- Tier D is the unknown/aggregator default and receives nothing.
- A Chinese-origin model on a Tier A host is downgraded to Tier B unless input isolation from the model developer is verified.
- Legacy host `local_command` providers are refused.

Owner declarations are visible and auditable; OFF_CRM cannot independently prove a provider's legal terms. The operator must verify each provider's console/policy page and update `terms_checked_at`.

## Defense layers

1. **Single gate:** runtime credentials are obtained only inside `EgressBroker`.
2. **Construction:** every task has an explicit allowlist payload builder.
3. **Preflight:** hard blockers run on the complete system-and-input packet before provider selection.
4. **Backstop redaction:** deterministic patterns replace phones, Indian mobile numbers, Aadhaar/PAN-like identifiers, and IP addresses.
5. **Trust and provenance:** effective tier is recomputed; a UI label cannot override policy.
6. **Quota and spend:** RPM, RPD, daily cost, and monthly cost limits fail closed.
7. **Same-tier failover:** fallback candidates crossing effective tiers are discarded; Tier C never fails over.
8. **No internal tools:** provider adapters expose text generation only.
9. **Exact audit:** every pending, succeeded, failed, and blocked call stores the exact final packet and provider identity.
10. **Human gates:** imported/generated drafts and template recommendations require human approval.

## Email handling

Email addresses remain in private parse results and CRM contact records. They are excluded by construction from generation packets; the scanner blocks an address even if it appears in free text.

Parse & send requires no model. Generate processes one POI at a time. Real addresses are associated locally with pending drafts after the model returns.

## Mailbox handling

The Gmail token path is known only to the connector/mail service. Production reply sync is restricted to thread IDs created by OFF_CRM. A reply flag is computed deterministically and stops future sends before another model call. Reply bodies are not used by the feedback loop.

The activity export is an owner-directed local download. It contains campaign/contact/message metadata, including received status and subjects, but excludes bodies and raw mailbox/provider payloads. Exporting it does not mark it provider-approved.

## Public web and prompt injection

Discovery accepts explicit public URLs and allowed domains, respects robots.txt and rate limits, blocks private/reserved network targets, bounds redirects/content/size, and stores normalized evidence instead of raw HTML.

Scraped content is data. It cannot choose a provider, change a trust tier, add payload fields, request internal retrieval, or bypass the scanner. Social data uses official APIs or verified manual import only.

## Sandboxed tools

Tool registration requires an immutable public GitHub commit and pinned image. Execution:

```text
docker run --pull=never --network=none --read-only
  --cap-drop=ALL --security-opt=no-new-privileges
  --user=65534:65534 --pids-limit=128 --memory=512m --cpus=1
  --tmpfs /tmp:rw,noexec,nosuid,size=64m
  -v <pinned-source>:/workspace:ro
```

Tool input passes the same email/secret/mailbox/context scanner. No CRM credentials or environment are deliberately injected. Docker remains a privileged host dependency; operators must patch Docker and restrict who can administer it.

## Acceptance tests

`tests/test_off_ai.py` verifies:

- private-person tasks are refused for Tier B/C/D;
- aggregators and China-jurisdiction hosts are downgraded;
- legacy local commands are refused;
- emails, credentials, mailbox queries, and context-store queries are blocked before the provider;
- internal fields are absent from the constructed payload;
- deterministic PII backstops run before egress;
- failover stays inside one tier;
- Tier C is excluded from failover;
- sandbox commands have no network, writes, privileges, or image pulls;
- GitHub tools require immutable commits and public-only inputs;
- private intake rows never appear in the API preview.

`tests/test_off_ai_sandbox_runtime.py` performs a real external connection attempt inside Docker when `OFF_CRM_SANDBOX_TEST_IMAGE` names an already-pulled pinned Python image. It is skipped, not faked, when Docker is unavailable.

## Secrets and local sensitivity

Never commit:

- `.env`;
- Google client-secret JSON or Gmail token;
- provider key material;
- `.provider_master.key` or `provider_secrets.enc`;
- local databases, attachments, outbox/inbox, exports, backups, or tool checkouts.

The egress audit contains approved payloads and provider responses. Project/chat history and intake private results are local private data. Protect `local_data`, OS accounts, backups, and the workstation itself.

## Known boundary

v0.12 is single-user and local-first. It is not a production multi-tenant security boundary. Before remote team deployment, add tenant-scoped authentication/authorization, PostgreSQL row isolation, managed secrets, durable workers, encrypted volumes, centralized audit retention, migrations, backup/restore drills, and network policy verification.

## Incident procedure

1. Disable the affected provider profile.
2. Pause campaigns and Gmail automation.
3. Preserve the database, provider profile registry, egress audit, campaign event log, and provider request IDs.
4. Revoke the provider key and Gmail token if exposure is plausible.
5. Inspect the exact egress packet and provider terms.
6. Correct the policy/test first, then re-enable the provider.
